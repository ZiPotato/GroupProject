# Final Project Presentation Guide

This guide helps you present your team project to the class with your team. It is based on the course paths, workflow expectations, and grading rubric.

The goal of the presentation is not only to show that your app works, but also to show how your team planned, built, tested, and improved the application.

## Main Goal of the Presentation

Your presentation should answer these questions clearly:

- What does the application do?
- If the project solved a specific problem, what was it?
- How did you divide the work and collaborate in GitHub?
- How did you test the project?
- What did you learn during the project?

---

## Recommended Length

Aim for about 10-15 minutes for the full presentation and demo.

Suggested timing:

- 3 minutes: introduction and project goal
- 3-5 minutes: live demo of the main workflow
- 2 minutes: teamwork and GitHub workflow
- 2-4 minutes: testing and code quality
- 1-2 minutes: reflection and lessons learned

---

## How to Divide the Presentation Between Partners

Both students should speak. A simple and fair split is:

- Partner 1: introduce the project, explain the user problem or goal, and start the demo
- Partner 2: continue the demo, explain GitHub workflow, testing, and reflection
- Both: answer class or teacher questions

If your team has 3 members, divide the same sections so that everyone presents at least one clear part.

---

## Recommended Presentation Structure

### 1. Introduce the Project

Start with the basics:

- Project name
- Team members
- Which path you chose: Path A or Path B
- Who the target user is
- What problem the application solves. If you did a game, explain the game concept and goal.

Example:

"Our project is RepairFlow. We built it for a small e-bike repair shop to help track repair requests from new request to completed work."

If you chose Path B, also explain briefly why the scope was realistic for 3-4 weeks.

### 2. Explain the MVP

Before the live demo, explain the minimum viable product.

- What were your 3-4 core features?
- What was intentionally left out?
- Which feature was the most important for the user?

This is important because the rubric evaluates whether the team completed the approved scope and whether the MVP is solid.

### 3. Demo the Main Workflow Live

The demo is the most important part. Show the main user flow from start to finish.

If you did Path A, your demo should normally include:

- add a repair request
- list repair requests
- change request status
- close or delete a request
- save and reload data

If you did Path B, show the approved core workflow of your own project from beginning to end.

During the demo:

- explain what the user is doing
- show that the app does not crash on normal mistakes
- keep the demo focused on the main workflow
- avoid clicking through every minor detail

It is better to show one complete user flow clearly than many features quickly.

### 4. Show How You Worked as a Team

After the demo, present evidence of teamwork.

Show or describe:

- commits and branches in GitHub
- pull requests, if you did reviews after each feature (this was not mandatory, but it is a good practice)
- code reviews or how you discussed code changes with the team
- GitHub Projects board or issues
- how work was divided between partners

You do not need to show every commit. Show just enough evidence to prove that both students contributed and that the team followed the course workflow.

Useful things to say:

- which features each partner implemented
- how you reviewed each other's code
- whether you had merge conflicts and how you solved them
- how the project board or issue list helped you stay organized

This part connects directly to the process section of the grading rubric.

### 5. Explain Testing and Reliability

Briefly show how you checked that your project works.

Include:

- what unit tests you wrote for core logic
- what functional tests you performed for the main workflow
- one example of invalid input or error handling

You do not need to present every test file line by line. Focus on what was tested and why it matters.

Example:

"We wrote unit tests for status changes so invalid transitions are blocked, and we also tested the full user flow manually from creating a request to saving and loading it again."

### 6. Reflect on What You Learned

Finish with a short retrospective.

Each partner should mention at least one learning point.

Good reflection topics:

- what went well in teamwork
- what was difficult when working together or with the implementation
- what you would improve next time
- what you learned about GitHub, pull requests, testing, or planning

This makes the presentation more credible and shows real understanding instead of only showing a finished product.

---

## What the teacher and classmates should see

Your presentation should make these things visible:

- the application works end-to-end
- the scope matches the chosen path
- both partners contributed
- GitHub workflow was used properly
- testing was taken seriously
- the team can explain technical and teamwork decisions clearly

If these points are visible, your presentation supports both the product and process areas in the rubric.

---

## Practical Tips Before Presenting

- Decide in advance who says what
- Practise once from start to finish
- Prepare demo data so you do not waste time typing everything live
- Close unrelated windows and notifications
- Keep your GitHub repository, board, and app ready before class starts
- Have a backup plan in case the live demo fails

Good backup options:

- screenshots of the app
- screenshots of pull requests or project board
- a short explanation of what should happen if a bug appears during the demo

---

## Simple Presentation Checklist

Use this checklist before class:

- [ ] We can explain the project problem and target user in 30-60 seconds
- [ ] We can show one complete main workflow without confusion
- [ ] Both partners have speaking roles
- [ ] We can show evidence of branches, PRs, reviews, and issues/project board
- [ ] We can explain our tests briefly and clearly
- [ ] We can name at least one thing we learned and one thing we would improve

---

## Short Presentation Template

You can use this structure directly:

1. "We are ..., and our project is ..."
2. "The target user is ..., and the problem is ..."
3. "Our MVP includes these core features: ..."
4. "Now we will show the main workflow."
5. "We worked with feature branches, pull requests, and code reviews. Partner 1 focused on ..., and Partner 2 focused on ..."
6. "We tested the core logic with ..., and we tested the main user flow by ..."
7. "What we learned was ..., and next time we would improve ..."

If you follow this structure, your presentation will stay clear, balanced, and aligned with the course expectations.

## Presentation platforms   

- The prentation will be done in the classroom using a projector. You can use your own laptop or a shared one. Make sure to have your project ready and tested on the machine you will present from.
- If you want you can create a PowerPoint, Google Slides or simple markdown file to structure your talk, but it is not required. The most important thing is to show the live demo of your application and explain your teamwork and testing process clearly.
